# Отчёт по баг-хантингу и аудиту проекта LiDAR IoT Network

В ходе ручного аудита исходного кода C++ (ESP32) и Python (Flask сервер) я обнаружил несколько критических и логических проблем, которые могли бы привести к нестабильной работе системы мониторинга на реальных объектах.

## 🚨 Найденные баги и уязвимости

### 1. [Критический] Потеря оффлайн-событий (Сервер)
* **Проблема:** В прошивке отлично реализован кольцевой буфер во Flash-памяти (LittleFS) для записи алертов без сети. При восстановлении сети прошивка выгружает накопленные события пакетом (массивом JSON) в топик `lidar/<sn>/offline_events`. 
**ОДНАКО** серверный Python скрипт (`mqtt_service.py`) **не подписывался** на этот топик и **не умел** обрабатывать массив объектов. Как итог, все оффлайн-алерты, сохраненные во время обрыва связи, молча исчезали при её восстановлении.
* **Статус:** ✅ **ИСПРАВЛЕНО МНОЙ.** Я добавил подписку на топик и научил `mqtt_service.py` корректно парсить массивы (батчи) и построчно сохранять их в БД с поддержкой формата выгрузки из C++ `flash_buffer.cpp`.

### 2. [Высокий] Риск 100% загрузки процессора при разрыве MQTT (Сервер)
* **Проблема:** В `mqtt_service.py` цикл `_run_loop` содержал `time.sleep(5)` только в блоке `except Exception`. Если MQTT брокер отключал клиента без вызова исключения (чистый graceful disconnect или сетевой таймаут Paho MQTT внутри цикла), метод `loop_forever()` завершал работу без ошибки, после чего цикл уходил в бесконечные мгновенные попытки реконнекта, загружая ядро CPU сервера на 100%.
* **Статус:** ✅ **ИСПРАВЛЕНО МНОЙ.** Блок паузы перенесён в `finally`, гарантируя ожидание 5 секунд перед любой новой попыткой соединения.

### 3. [Средний] Логическая петля UDP Auto-Discovery (Сервер)
* **Проблема:** Сервис `DiscoveryService` отправлял Broadcast пакеты на порт `44444` (`<broadcast>:44444`) и сам же слушал порт `0.0.0.0:44444`. Из-за этого сервер бесконечно "слышал" сам себя каждые 3 секунды.
* **Статус:** ⚠️ Оставлено как есть, так как в коде есть защита от обработки своих пакетов (`if msg.get("role") == "esp32_client"`). Это не приводит к сбоям, но создаёт небольшой лишний фон в консоли.

### 4. [Средний/Низкий] Отсутствие ответа `ALERT_RESTORED` при разбитии стекла (Прошивка)
* **Проблема:** В `monitoring_manager.cpp` есть логика: если датчик был чем-то перекрыт (алерт о заклеивании), но затем стекло полностью разбили (дистанция ушла в бесконечность), таймер перекрытия сбрасывается (`obstructionStartMs = 0;`), и отправляется `ALERT_DESTRUCTION`. Однако алерт `ALERT_RESTORED` (о снятии перекрытия) не отправляется.
* **Статус:** 💡 Это логично в рамках ТЗ (стекло уничтожено, а не очищено), но для базы данных сервера это будет выглядеть как незакрытое перекрытие. Рекомендуется учесть этот кейс при разработке фронтенда дашборда.

### 5. [Замечание] API Key защита
* В `app.py` внедрен механизм проверки `X-API-Key` заголовка. Если вы решите установить `API_KEY` в `config.py`, убедитесь, что фронтенд (JS) настроен на его передачу при AJAX-запросах, иначе веб-интерфейс не сможет отправлять команды.
